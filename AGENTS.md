# Acorn Contracts: Agent Guidance

Procedural rules for working in this repo. See `README.md` for what each API is and why it's shaped the way it is; this file is about how to do the work correctly.

## Adding a new component

Writing `component-api/<id>.json` and updating `manifest.json` is not enough to make a component show up on the live site (`index.html`). The nav, home tables, and per-item view are all driven by a separate, hardcoded `DATA` array inside `index.html`'s own `<script>` block, alphabetized by name. Add a matching entry there too (`id`, `name`, `group`, `figma`, `supernova`, `storybook`, `kind`, `tagName`, `file`), in alphabetical position. Without it, the component is fully documented in the data but invisible in the UI.

`check-index-data.py` now errors on exactly that (run by `check-contracts.yml`): it asserts the two id sets match and that `kind`, `tagName` and `file` agree wherever both sides name them. It does not remove the need to write the `DATA` entry by hand, it just means forgetting fails CI instead of failing silently. Deliberate divergences go in that script's `EXCEPTIONS` with a reason, and are printed on every run rather than passing quietly.

**Verify `figma`/`supernova` with real evidence, don't guess.** These mean whether the real Firefox component (not Acorn's own) has a citation in Firefox's own internal Figma/Supernova instance. Check via the Supernova MCP:
- `sn_get_component_list` (paginate via `cursor`) for canonical Supernova components.
- `sn_get_figma_component_list` (paginate via `cursor`, ~300+ entries) for real Figma component records; search the full list by the component's real name (e.g. "Five Star", "Button group"), not just the first page.

A component with no matching name in either list gets `figma: "no"` / `supernova: "no"`, not an omitted field or a guess. As of 2026-09-01 this Supernova connection covers real Firefox chrome/toolkit components (not just Acorn's own), confirmed by finding real matches like "Toolbox", "Tabstrip", "Bookmarks Toolbar" in the list.

**Verify `storybook` with a real check, don't infer from directory structure.** A component's own subdirectory existing under `toolkit/content/widgets/` doesn't mean it has a story; check for a real `<name>.stories.mjs` file specifically (a quick sparse `git fetch` scoped to `toolkit/content/widgets/*/*.stories.mjs` works, see `component-api/check-drift.py` for the same clone technique).

## Syncing with upstream

`token-api/sync.py` is a real rerunnable pipeline (see `token-api/README.md`). `component-api/` has no equivalent full-regeneration script; `component-api/check-drift.py` only detects which tracked components' real source changed and which real `toolkit/content/widgets/` components have no entry yet (see `component-api/README.md`). Writing or updating an actual `component-api/<id>.json` entry still means reading the real current source yourself (or delegating to an agent) and following the schema, same as before drift detection existed.

## Checking whether a token/CSS custom property exists in Figma

The same "verify with real evidence, don't guess" rule above applies one level down too: every component page's Design tokens table has an "In Figma" column (built from `token-api/figma-token-map.json`, see `token-api/README.md`'s "Figma existence check" section for the exact pipeline and matching rule). **This check hits the Figma REST API directly, never Supernova** — Supernova's sync of this design system has known gaps elsewhere in this project family (it couldn't even confirm its own token source file was the same file as "Nova Styles"), so it is explicitly not trusted as the source of truth for token/variable-existence checks anywhere in this project family. Two things worth knowing before touching that column or its data:

- **codeSyntax is not a usable signal, even on the direct Figma API.** It was checked directly (every variable's own `codeSyntax` field in the fetched dump) before falling back to name matching, not assumed unusable just because a prior Supernova-based pass lacked the field at all. The direct API does expose `codeSyntax`, but only 2 of 718 real variables in the file have it populated, far too sparse to be a general signal. If a future Figma publish starts populating it broadly, check again before continuing to trust name-based matching.
- **A confirmed "no" is a real, common, expected finding**, not evidence something is broken: entire component families (urlbar, panel, toolbar, sidebar, checkbox, most `moz-*` components) have no matching *semantic color* group in this Figma file at all. Don't "fix" a row full of `no`s by loosening the match rule; loosening it enough to turn those into false `yes`es defeats the entire point of a real existence check.
- **Do not resolve a token's alias chain to backfill a match under a different name.** `resolve.py` records every token's real alias chain in `resolved/*.json` (e.g. `--box-button-background-color` resolves through `button.background.color.menu.@base`), and it's tempting to check those hops against Figma to shrink the `no` bucket — this was tried and explicitly rejected. This column's whole point is catching Figma and code drifting apart *by name*; counting a match through an indirectly-aliased, differently-named variable hides exactly that drift. Whether a value is reachable through some other Figma variable under the hood is a different question from whether Figma and code agree on this name — this check only ever answers the second one.
- **This is a strict two-state check (`yes`/`no`), not three.** A one-word-off near miss used to get its own `ambiguous` status; also rejected, same principle as above: "if it doesn't match something we see in figma/the import file then it doesn't exist... that's the goal, are these syncing." A near miss is real signal that a name has drifted, not an unresolved maybe. It's still recorded as `no`, with `matchType: "near-miss"` and the close-but-wrong `matchedPath` kept as a diagnostic (visible in each row's tooltip, useful for spotting a systematic gap across a whole family), but never rendered as anything other than a confirmed miss.

Regenerating `token-api/figma-token-map.json` is a two-step process: refreshing `token-api/figma-variables-dump.json` is a single, fully scriptable, credential-scoped REST call (`GET /v1/files/Co6vXnF5SiQMcJ7UoJvZX6/variables/local` with an `X-Figma-Token` header) — no agent session or MCP connection needed at all, unlike the Supernova-based version this replaced — then `python3 token-api/figma-check.py` turns that dump into the map. See `token-api/README.md` for both steps in full.
