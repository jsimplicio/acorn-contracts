# Acorn Contracts

Machine-readable contracts documenting REAL Firefox design-system components: what their real API surface is (`component-api/`), how to actually use them (`guidance-api/`), and what real design tokens they're built from (`token-api/`). Everything here documents mozilla-central itself, not any other naming or structure.

A small site (`index.html`, `python3 serve.sh` to view it, and published to GitHub Pages by `.github/workflows/pages.yml` on every push to `main`) renders all three live. Start there for the human-readable version; this README and `manifest.json` are for a consumer who wants the raw data directly.

## `manifest.json`

The one file that spans all three APIs: for every real component id, which of `component-api/`, `guidance-api/`, and `token-api/` actually has data for it, and (for token-api specifically) which real basename(s) it resolves to. This is the entry point for discovery, an agent shouldn't have to probe 57+ URLs or parse `index.html`'s JavaScript to find out what exists.

```jsonc
{
  "generated_at": "2026-08-17T21:59:00Z",
  "apis": { "componentApi": "component-api/<id>.json", "...": "..." },
  "components": {
    "button": {
      "componentApi": true,
      "guidanceApi": true,
      "tokenApi": true,
      "tokenBasenames": ["button"],
      "novaTokenBasenames": ["button"]
    },
    "...": { "...": "..." }
  }
}
```

Generated by `build-manifest.py` from the three directories' real contents, and `build-manifest.py --check` fails if the committed copy has drifted. Rerun it after adding or removing an id in any of the three directories, or after a token sync changes which basenames resolve.

## Keeping it current

Several checked-in files are derived from others, and **no sync regenerates them for you.** The order matters, because each step reads the previous step's output:

```sh
python3 token-api/sync.py         # 1. fetch + convert real upstream tokens (network)
python3 token-api/resolve.py      # 2. re-resolve: sync.py just rewrote its inputs
python3 token-api/figma-check.py  # 3. re-check names: resolved/ and base/ moved
python3 build-manifest.py         # 4. token basenames may have changed
python3 build-search-index.py     # 5. any of the above, or any README edit, feeds this
```

`update-meta.py` is the one exception to the order: it reads this repo's own git history, so it runs *after* committing a change to `component-api/` or `guidance-api/`, not before.

`component-api/figma-check.py` is a second exception: it runs on its own schedule, not as part of this chain. Re-run it whenever `component-api/figma-components-dump.json` gets re-pulled (see `component-api/README.md`), and pass `--advance` only once its diff has actually been triaged.

**Steps 2-5 are the easy half to forget, and forgetting them is silent.** A stale derived file still validates against its schema and still looks plausible. Both have really happened: `token-api/resolved/` once sat 27 files out of date, and `manifest.json` reported eight components as having no guidance when they had it. Each derived file therefore has a CI guard in `.github/workflows/check-derived.yml`. Treat that as the backstop, not the reminder — run the chain locally and CI has nothing to say.

**`component-api/` has no sync at all, deliberately.** `check-drift.py` reports which tracked components' real source moved and which real widgets have no entry yet; writing an actual `<id>.json` still means reading real upstream source, which is why there is no pipeline (see `component-api/README.md`). A plain run is read-only and safe to repeat. `--advance` stores this run's hashes as the new baseline, which records every finding as checked whether or not anyone acted on it, so pass it only once the findings are triaged. `AGENTS.md` has the triage procedure.

**`--ref <branch-or-sha>`** pins `sync.py` or `check-drift.py` to a specific upstream commit rather than the default branch tip, for reproducing an old sync or holding one steady.

## Dependencies

**One, `jsonschema`, and only for `validate-schemas.py`.** Everything else in
this repo is Python standard library.

```sh
python3 -m pip install jsonschema   # the only install this repo needs
python3 serve.sh                    # view the site locally
```

| what | status |
|---|---|
| Third-party Python | `jsonschema` |
| Everything else | stdlib: `json`, `re`, `glob`, `os`, `sys`, `pathlib`, `subprocess`, `hashlib`, `tempfile`, `argparse`, `collections` |
| Node / npm | none. No `package.json`, no lock file, no `node_modules` |
| Site runtime | none. `index.html` loads no CDN, no framework, no external script |
| CI installs | `jsonschema`, one line in `check-contracts.yml` |

This is deliberate, not incidental. Generating `component-api/` with a
Custom Elements Manifest analyzer was considered and not adopted: it would
have introduced a Node toolchain and its dependency tree to produce data
that still needs a human reading real source, which is why
`component-api/README.md` says there is no regeneration pipeline here.

The pre-push hook degrades gracefully when `jsonschema` is absent rather
than failing, so a fresh clone with no installs can still run every other
check.

`component-api/check-drift.py` and `token-api/sync.py` reach the network,
but only through `git` and only when run deliberately. Nothing in CI or in
the pre-push hook does.

## Versioning

`manifest.json` carries a `schemaVersion`. Bump it when a published field
changes shape, so a consumer can detect the change instead of breaking
quietly.

**It is `0.x` on purpose.** Per semver that means the shape may change at
any time and should not be treated as stable, which is the honest position:
nothing consumes this data yet, fields are still landing, and an
attribute's `type` moved from a bare string to CEM's `{ "text": ... }`
object as recently as 2026-09-15. Before `0.1.0` there was no signal at
all, so a consumer built against the old shape could not have detected that
change.

`1.0.0` would mean something specific and is not claimed yet: a real
consumer exists, and this repo is willing to keep the shape stable for it
or to bump a major version when it cannot. Until both are true, `0.x` is
the accurate label.

## What is machine-readable, and what is not yet

Everything in `component-api/` and `token-api/` is data validated against a
real JSON Schema on every push, so a consumer can enumerate components,
their attributes, slots, events, methods, CSS custom properties, tokens,
inheritance and Figma wiring without parsing prose. Four gaps are worth
knowing before you build against it. Each one says how to recount it, since
a number written here would go stale.

**1. Not every enumerated attribute declares its legal values.** An
attribute whose `type.text` is a bare `"string"` may still only accept a
fixed set; where that set has been established it is written as a
TypeScript-style union, and where it has not, `"string"` is all the
contract honestly knows. The gap is concentrated in components with no
Figma Code Connect file, where nothing external could contradict a guess.

```sh
# axes that have a union vs. those that do not
python3 - <<'PY'
import json, glob, os
for p in sorted(glob.glob("component-api/*.json")):
    b = os.path.basename(p)
    if b.startswith("_") or b in ("schema.json", "drift-manifest.json"): continue
    d = json.load(open(p)); attrs = {a["name"]: a for a in d.get("attributes") or []}
    for v in d.get("variants") or []:
        a = attrs.get(v["axis"])
        if not a: continue
        t = (a.get("type") or {}).get("text") or ""
        if t in ("boolean", "number"): continue
        print(("union " if "|" in t else "PLAIN "), d["id"], v["axis"])
PY
```

**2. `implementation.kind` is asserted, not derivable.** Nothing records
what a class extends, so `modern` vs `classic` is a human judgement made by
reading source. A machine has to take it on trust. CEM has `superclass` and
`mixins` on a class declaration for exactly this, and neither is populated
here. The live risk is an upstream XUL-to-Lit port silently invalidating a
`classic` entry.

**3. `implementation.verifiedAt` is sparse on purpose.** It records when an
entry's contents were last confirmed against real upstream source, and is
deliberately not backfilled: for most entries nobody knows the answer, and
inventing a date would be exactly the fiction the rest of this directory
avoids. An absent `verifiedAt` means unconfirmed since the field existed,
not recently confirmed.

**4. `implementation.file` is absent for `missing` entries.** It is
otherwise always a bare path, never a path plus prose. A `missing`
component has no source-of-truth file by definition, and what exists
instead is described in `description`, so check for the key rather than
assuming every entry has one.


**Not a gap, by design:** `guidance-api/` is prose and will stay prose. Per
the Nathan Curtis distinction this project is built on, specs say how to
build and guidelines say how to use; only the spec half can be structured.

## The three APIs

- **[component-api/](component-api/README.md)**: real attributes, slots, events, methods, CSS custom properties. Read out of real source by hand, entry by entry, and shaped with CEM's field names. A spec, but not a generated one: see that README on why there is no regeneration pipeline.
- **[guidance-api/](guidance-api/README.md)**: real do's and don'ts, editorial, written by a human (or an agent reasoning carefully about real usage), not extracted from code. A separate artifact from component-api on purpose, see its README for why.
- **[token-api/](token-api/README.md)**: real Firefox design tokens, converted to W3C DTCG format, synced from the actual upstream repo. Includes a pre-resolved export (`token-api/resolved/`) for a consumer who just wants the final value.

Each has its own `schema.json` (real, machine-checkable JSON Schema, not just prose) and `_meta.json` (component-api/guidance-api only: each file's real last-commit date from this repo's own git history, not a fabricated timestamp).
