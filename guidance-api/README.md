# Guidance API

The Guidance API captures do's, don'ts, and the single most load-bearing runtime fact about a component, surfaced in one obvious place even when it's already stated quietly somewhere in component-api: usage advice, common mistakes, and real behavior, not a restatement of what an attribute does but what actually happens, and when. This is the second half of a two-part documentation-data effort. The first half is the **[Component API](../component-api/README.md)**, a Custom Elements Manifest (CEM)-shaped structural spec: real attributes, slots, events, and methods, read out of real source entry by entry.

## Why this is a separate API, not a field inside the Component API

CEM, and API-shaped data generally, only models structural surface: what attributes exist, what type they are, what slots and events a component exposes. That is the half of the job a parser could in principle do, whether or not one is used here.

Do's and don'ts are categorically different. They require human judgment about real usage patterns and real mistakes. Nothing in `moz-button`'s source tells you "don't set `type=\"split\"` without `menuId`, the chevron renders but has nothing to open": that's a failure mode someone has to have seen, understood, and written down. It isn't in the type signature.

`behavior` entries are a third category, added after a real, stated need: a spec-driven exercise testing whether component-api + token-api are rich enough to actually build a component (see `COMPONENT-TESTS.md`) kept finding that the single most load-bearing runtime fact about a component, which of two real implementations renders under what condition, what sequence a dismiss or toggle actually fires in, was easy to miss. Piloting it on 3 real entries (select, message-bar, card) found something worth stating plainly: in all 3 cases the fact was already there, quietly, in an attribute or event's own `description` (`select.usePanelList`, `message-bar`'s two dismiss events, `card`'s `toggle` event). `behavior` isn't filling a hole CEM structurally can't express, these 3 pilots prove it can; it's surfacing the one fact worth leading with, in one consistent, neutral-toned place, the same service dos/donts already does by restating a real fact as actionable advice instead of leaving it buried in a field someone has to think to open. Still categorically the same as dos/donts in one way: someone has to have read the real source and written it down, it isn't extracted.

This maps directly onto a distinction Nathan Curtis (EightShapes) draws for design systems documentation: **specs say how to build, guidelines say how to use.** The Component API is the spec half, mechanical, generated by parsing source. This Guidance API is the guidelines half, editorial, written by a human (or an agent reasoning carefully about real usage) rather than extracted from code, `behavior` entries included: they're closer in spirit to spec (neutral fact, not advice) but can only be produced the guidelines way, by someone reading real source, so they live here rather than in component-api.

Keeping them as two separate, independently-produced artifacts rather than merging guidance fields into the Component API preserves that production distinction: one pipeline parses source and can be regenerated automatically any time the component changes; the other is authored content that only changes when someone deliberately revisits it. Collapsing them into one file would make it easy to assume the whole file is machine-derived and trustworthy in the same way, when the guidance half is not.

## Schema

```jsonc
{
  "id": "button",                 // matches the Component API's id exactly, this is the join key
  "dos": [
    { "text": "Use menuId pointing at a panel-list instead of writing custom open and close logic." }
  ],
  "donts": [
    { "text": "Don't set type=\"split\" without menuId, the chevron renders but has nothing to open." }
  ]
}
```

A `behavior` entry, from a different real component (`select`), where that's the field actually doing work:

```jsonc
{
  "id": "select",
  "dos": [],
  "donts": [],
  "behavior": [
    { "text": "Renders a native <select> when no moz-option has an icon; switches to a custom panel-list/button combo the moment any option has one (internal usePanelList state), a real condition, not a style choice." }
  ]
}
```

Field by field:

- **`id`** (string, required): An implementation-agnostic slug. Must match the `id` used for the same component in the Component API exactly, this is the join key that lets a consumer look up both the spec and the guidelines for one component. Not a tag name: some entries (like `toolbox`) have no real custom element behind them at all.
- **`dos`** (array of objects, required, may be empty): Things to do. Each entry is `{ "text": "..." }`, one sentence describing a specific, actionable practice, not a restatement of what an attribute does.
- **`donts`** (array of objects, required, may be empty): Things to avoid. Each entry is `{ "text": "..." }`, ideally naming the concrete symptom of getting it wrong (as in the button example above: not just "don't do X" but "don't do X, here's what breaks").
- **`behavior`** (array of objects, optional, may be absent): Real runtime facts, not advice: what condition picks between two real implementations, what actually fires and when, what real DOM element backs a stated interaction. Each entry is `{ "text": "..." }`, a neutral statement of fact citing something concrete (a property, method, or real element), the same citation bar as dos/donts, just without a "do" or "don't" framing. Most entries don't have this field yet; it was added for a real, specific need (see above), not spread across the whole inventory speculatively.

That's the whole schema. No `severity`, `tags`, `author`, `dates`, or similar metadata fields, they were deliberately left out. Add a field only when there's a clear, stated need to support real consumption of this data; don't add one speculatively.

## Files in this directory

| File | What it is |
|---|---|
| `<id>.json` | One per component, matching the `id` used in the Component API. |
| `_skeleton.json` | Empty templated example of the shape, for authoring a new entry. |
| `schema.json` | The shape above as a draft 2020-12 JSON Schema. Enforced by `validate-schemas.py` on every push. |
| `_meta.json` | Per-id `lastCommit`/`lastModified` from this repo's own history, plus the `HEAD` it was generated against. Says when the JSON was last edited here, not when it was last verified against Firefox source. |

**Entries with no widget class are deliberate.** Toolbar, Toolbox, Sidebar,
Bookmarks Toolbar, URL Bar Action/Identity/Result, Panel Separator, Page Nav
Separator, Chip and Details are the same kind of case, real user-facing
real, user-facing surfaces worth documenting even with no dedicated widget
class behind them.

## Coverage

Guidance does not cover every component in the inventory. The components
still missing one are enumerated in `check-index-data.py`'s `GUIDANCE_GAPS`,
which is also what enforces the list: a new component with no guidance, or a
guidance entry whose id matches no contract, fails that check. Deliberately
not restated here as a count or a list, because the last version of this
sentence said all 57 components were covered and went quietly wrong the
moment the inventory grew to 71. Run `python3 check-index-data.py` for the
current numbers.

Every entry that does exist is grounded in the component's real source (a specific method, property, or lifecycle behavior), not generic UX advice, including the entries with no dedicated widget class: their guidance points to the real file or singleton that actually owns the behavior instead.
